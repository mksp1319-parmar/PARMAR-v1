# PARMAR Chat — Regression Risk Register

**Status:** Phase 1 risk assessment; review before implementation.
**Scale:** P0 = release blocker/security boundary; P1 = high user/data or misleading-capability risk; P2 = significant UX/compatibility risk; P3 = lower-impact polish risk.

| ID / Priority | Risk | Evidence and affected paths | Mitigation / required tests | Release gate |
|---|---|---|---|---|
| R-01 / **P0** | Enabling authenticated Chat by bypassing the atomic fence weakens the protected execution boundary. | `safety/runtime_no_go.py::require_atomic_authorization_fence`; `interface/futuristic_app.py` `/api/chat`; `chat/service.py`; authenticated HTTP tests. | Implement a security-approved atomic authorization/effect fence. Test identity/profile/session revocation and concurrent change before effects, approval-required requests, provider call counts, and fail-closed behavior. | No authenticated generation until security sign-off and adversarial tests pass. |
| R-02 / **P1** | A future handler refactor could move conversation creation or provider execution ahead of the authenticated-chat fence, causing protected side effects on a denied request. This is a regression risk, not a current defect. | `interface/futuristic_app.py` currently calls `_deny_unfenced_protected_operation(... AUTHENTICATED_CHAT ...)` before conversation creation/lookup; `tests/test_conversation_http.py` asserts denied requests do not invoke ChatService or create an owned conversation. | Preserve guard ordering and the zero-provider-call/zero-persistence assertions when changing the route or authorization contract. | Any fence change must keep all denied preflight cases at zero provider calls, writes, and quota usage. |
| R-03 / **P1** | Users interpret Local Demo, provider inventory, or the Chat workspace as a working conversational model. | `chat/providers.py::provider_from_environment` defaults to Local Demo; anonymous request path forces Local Demo; `GET /api/providers` reports `NOT_CHECKED`; no Chat selector. | Label Local Demo as deterministic/non-conversational; keep unavailable status explicit; separate configured/authorized/reachable/request succeeded. | R-15 / **P2** | A stop control reports cancellation while the HTTP/provider request continues, consumes resources, or later persists output. | Current one-shot POST has no AbortController or server cancellation endpoint; request sequence only drops stale client result. | Do not show Stop until transport and backend/provider cancellation semantics are implemented and acknowledged. | R-16 / **P2** | Generic catch/error status hides whether provider, policy, storage, or auth failed, encouraging unsafe retries or incorrect user assumptions. | `app.js::submitChatMessage` catches broadly and restores prompt with generic message; backend normalizes some provider errors; history has specific retry state. | Add typed public error contracts without leaking secrets; preserve draft and explicit user retry; do not automatically fall back to another provider. ## Mandatory no-go conditions

Stop or keep the capability unavailable if:

- The atomic authorization fence is absent or not security-approved.
- Provider/model selection bypasses server authorization or falls back silently.
- A feature cannot honestly disclose whether it is configured, authorized, reachable, or completed.
- The app cannot prevent unvalidated candidate output from being exposed as released.
- Attachments have no documented egress, retention, deletion, ownership, or resource-limit behavior.
- A mutation API cannot enforce active owner/profile and CSRF at effect time.
- Tests use mocks as the only evidence but the release report claims live service or device functionality.
