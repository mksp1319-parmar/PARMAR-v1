# PARMAR Chat Providers

The chat path is PARMAR analysis and enforcement -> `ChatContext` -> provider readiness -> external authorization (for non-local providers) -> `AIOrchestrator` capability matching -> `ChatRouter` / selected adapter -> untrusted response -> PARMAR response handling. Safety decisions remain PARMAR's authority; provider text cannot approve, execute actions, alter policy, or modify memory.

PARMAR is an orchestration layer, not the owner of third-party AI systems. Provider/model configuration depends on actual server-side settings; readiness inspection does not test reachability. No universal “best AI” ranking is used. `SINGLE_PROVIDER` remains the default. The opt-in `VERIFIED_MULTI_MODEL` execution method accepts two to three registered, independent candidates and runs them sequentially once each with copies of the same sanitized task/context. “Verified” means only deterministic PARMAR-side exact/normalized text agreement; it is not proof of correctness. Disagreement returns candidates without selecting a winner. Partial success is not verified, and failures are normalized. Non-local multi-model execution requires both the explicit authorization policy and `PARMAR_VERIFIED_MULTI_MODEL_EXTERNAL_ENABLED`; this phase uses injected fake providers only and makes no real inference calls.

`GET /api/providers` exposes safe configuration/readiness metadata only. Configuration presence does not mean reachability and does not authorize external use. The server-side external authorization allow-list defaults to deny and is separate from PARMAR safety approval. External verified multi-model execution requires both explicit mode authorization and the global feature guard. Legacy `/api/chat` requests remain single-provider; only an explicit `orchestration_mode: "VERIFIED_MULTI_MODEL"` opts in. Client payloads cannot set endpoint URLs, model IDs, credentials, or adapters.

Implemented adapters are `LocalDemoProvider`, generic `HTTPChatProvider`, `OpenAIChatProvider`, `GeminiChatProvider`, and `ClaudeChatProvider`. The local demo is the deterministic default and makes no network request. External provider requests are complete/non-streaming and the default HTTP transport does not follow redirects. Adapters are fake-transport tested, but this repository contains no provider credentials and no external provider is configured.

Set `PARMAR_CHAT_PROVIDER` to `local-demo`, `http-json`, `openai`, `gemini`, or `claude`. Empty/unset means `local-demo`; unknown or incomplete explicit configuration fails safely and never falls back to another provider.

For `http-json`, set `PARMAR_CHAT_ENDPOINT`, `PARMAR_CHAT_MODEL`, and `PARMAR_CHAT_API_KEY`. For `openai`, set `PARMAR_OPENAI_MODEL` and `PARMAR_OPENAI_API_KEY`; `PARMAR_OPENAI_ENDPOINT` is optional. For `gemini`, set `PARMAR_GEMINI_MODEL` and `PARMAR_GEMINI_API_KEY`; `PARMAR_GEMINI_ENDPOINT` is optional. For `claude`, set `PARMAR_CLAUDE_MODEL` and `PARMAR_CLAUDE_API_KEY`; `PARMAR_CLAUDE_ENDPOINT` is optional. `PARMAR_CHAT_TIMEOUT_SECONDS` is shared (default 30, maximum 120).

Credentials are read from environment variables, sent only in provider authentication headers, and excluded from prompt/context/response handling. Real provider access requires the user's own credentials and may incur charges. No SDK dependencies were added.
External single-provider authorization is separate from provider configuration and pricing eligibility. It defaults to deny and is configured only on the server with `PARMAR_EXTERNAL_CHAT_ENABLED`, `PARMAR_EXTERNAL_CHAT_ALLOWED_PROVIDERS`, `PARMAR_EXTERNAL_CHAT_ALLOWED_CAPABILITIES`, and `PARMAR_EXTERNAL_CHAT_ALLOW_SINGLE_PROVIDER`. Boolean values must be explicitly `true` or `false`; provider and capability allow-lists are comma-separated. Missing or malformed settings deny external use. Supported external provider IDs are `http-json`, `openai`, `gemini`, `claude`, and `http-json-search`; supported capability IDs include `web_search` in addition to `text_generation`, `reasoning`, `code_generation`, `summarization`, `translation`, `structured_output`, `verification`, and `image_analysis`. The local demo is not controlled by external authorization. Verified multi-model authorization remains separately gated and disabled by default.

These authorization settings do not override `ProviderFreePolicy`. Gemini's exact `gemini-3.7-flash` model is allow-listed because Google's official model catalog lists it and the pricing page lists Standard Free Tier input and output as free of charge. Other Gemini model IDs remain blocked. OpenAI and Claude remain unavailable under their `PAID_ONLY` records, even when credentials and external authorization are configured. Free Tier availability and rate limits are project-specific; this policy does not verify the configured Google project's billing tier, remaining quota, key validity, or reachability. Use a Google Free Tier project and monitor its rate limits. Readiness performs no provider request and does not establish reachability.

## Real research/search foundation (Phase 4A)

`POST /api/chat` accepts the optional boolean `"research": true` to request a PARMAR-governed search before Chat response generation. The existing Research-in-Chat control in the Chat composer, and the corresponding explicit VOKKI option, request this mode; ordinary Chat remains unchanged when research is not selected. A pending approval stores only the research-mode boolean, not retrieved sources, and cannot search until the existing approval continuation establishes the authoritative approved enforcement boundary.

Search is a separate capability, not a Chat or VOKKI provider. No search provider is selected by default. Configure `PARMAR_SEARCH_PROVIDER=http-json` and `PARMAR_SEARCH_ENDPOINT` to select the generic JSON search adapter. The endpoint accepts a JSON `POST` of `{"query":"...","limit":20}` and must return `{"results":[{"title":"...","url":"https://...","source_id":"...","snippet":"...","metadata":{"author":"...","attribution":"...","content_type":"...","published_at":"..."}}]}`. `title`, HTTPS `url`, and `source_id` are required. PARMAR derives and validates the domain from the URL; only the listed attribution metadata is retained. Unknown provider fields are discarded. Duplicate destinations are returned once.

Set `PARMAR_SEARCH_API_KEY` only if required by the selected endpoint; it is sent as a bearer header, never in the query or request body. `PARMAR_SEARCH_TIMEOUT_SECONDS` defaults to 15 and is capped at 30. Search response bodies are capped at 512 KB. Only HTTPS endpoints are accepted, except explicitly configured loopback HTTP endpoints for local adapters; DNS results are checked and pinned to public addresses (or loopback addresses for the local exception), environment proxies are disabled for search, and redirects are not followed. Provider configuration alone does not authorize search: the server must also explicitly allow both `http-json-search` and `web_search` in the external authorization allow-lists and set the existing external authorization booleans. There is no silent fallback to another adapter. Missing configuration, failed requests, malformed provider responses, no results, and blocked requests have distinct versioned research states. Search output is untrusted data and never changes PARMAR policy, approval, or enforcement authority.

The research contract is version `1.0` and includes status plus validated source title, normalized usable URL, derived domain, provider/source identifiers, optional snippet, and allow-listed attribution metadata. Validated research status and sources are atomically stored only with the exact assistant message whose existing response-release contract is `RELEASED` and response-safety status is `PASS`; history returns those sources with that message. Pending, blocked, failed, or withheld results do not expose or persist source metadata. Conversation deletion through the repository cascades to associated research metadata. This local SQLite data is not encrypted at rest.

Sources are attribution, not proof that every generated claim is factually supported by them. Retrieved content is untrusted context and never changes request review, risk classification, enforcement, ActionBoundary, approval, provider authorization, or response-safety authority. Research is never automatically copied into durable Memory.

# PARMAR V1

PARMAR — Predictive AI-Risk Mediation & Autonomous Reasoning

PARMAR is a human-centered AI safety and decision-support system. It analyzes a proposal, evaluates risk and conflict, applies independent safety checks, and requires explicit human approval before any consequential action.

## Core design

- Intent analysis identifies the likely goal and action.
- Risk engine scores the proposal across multiple risk categories.
- Conflict detector compares the proposed action against human interests and rules.
- Mediation engine proposes safer alternatives and explanations.
- Independent safety checks block privacy or autonomy violations.
- Emergency gate stops or escalates high-risk proposals.
- Decision engine writes a structured proposal that requires human approval.

## Privacy-safe phone awareness module

The phone-awareness component is intentionally conservative and local-first.

What it does:
- evaluates simulated phone-related awareness events
- checks for explicit permission state
- minimizes data collection to benign metadata only
- flags privacy-sensitive signals such as microphone, camera, message, contact, and location access
- requires explicit human approval for higher-risk events
- logs a sanitized audit record

What it does not do:
- it does not read real private messages, photos, contacts, or chat content
- it does not access microphones, cameras, or location data without explicit permission and a feature that requires it; VOKKI voice input, when supported, starts only after a Talk press and uses browser-enforced on-device speech recognition
- it does not attempt to bypass device, OS, browser, or app security controls
- it does not run hidden background monitoring

## Human oversight rule

HUMAN OVERSIGHT IS MANDATORY.
PARMAR never independently executes a consequential action or overrides a human decision.

#### Process-boundary preparation

The current desktop implementation uses one Electron main process for the PARMAR control window and the AETHER browser window. Electron's single-instance lock prevents a second application instance from registering another set of handlers or creating duplicate control windows. This is not process or network isolation: the AETHER `BrowserWindow`, tab `WebContentsView`s, Electron main process, and their Chromium descendants are not launched under a dedicated network boundary. The control window and its loopback backend access therefore cannot be separated from browser networking by applying a namespace to the current whole application.

The future design should keep PARMAR and its backend outside the browser namespace and have a separately launched AETHER browser process own its browser chrome, tab views, persistent browser session, and browser storage. The PARMAR Electron main process remains in the host namespace and launches a separate Electron process from the pinned runtime with an explicit browser-child entry mode; only the unshare wrapper, verifier, browser Electron main process, and its Chromium descendants inherit the child network namespace. The child mode must create only AETHER's browser window and must not start/connect a PARMAR backend. Launch must occur only through a reviewed security wrapper after it verifies namespace membership, restrictive IPv4/IPv6 policy, proxy availability, and process identity. There must be no direct Electron launch fallback when that wrapper is absent or fails. Parent shutdown must terminate and verify all browser descendants before releasing only resources owned by that launch; browser crash or broker loss must not restart the process outside the wrapper.

#### Offline namespace prototype (not an Electron launch path)

`desktop/isolation-launcher.cjs` starts a fixed Node probe, not Electron. The PARMAR/test parent remains in its original network namespace; it does not launch or move the PARMAR backend. `unshare --user --map-root-user --net` places the child in a fresh user and network namespace. A static bootstrap shell and its short-lived Node, `ip`, and `nft` verifier processes run inside that namespace; after checks pass, the shell execs `setpriv` and the fixed probe in the same process slot. The probe runs with its capability bounding set dropped and `NoNewPrivs` enabled, then rechecks namespace identity, interfaces/routes, and privilege state. Only the probe remains as a long-lived process in this prototype. Its only inherited IPC is stdin/stdout with the fixed status/stop message shapes, a launch capability, sequence checks, and a 30-second capability expiry; broker EOF causes the probe to exit. The child is placed in a separate process group, and the parent kills that group on stop, startup failure, timeout, or broker disconnect. A live process fixture test verifies group cleanup for a generic parent and its descendant; that test does not prove Electron or Chromium descendants will remain in or be terminated with this group. There are no commands, filesystem, PARMAR API, approval, or webpage-content operations on this channel. This pipe prototype does not authenticate kernel socket peer credentials and is not suitable as the production broker.

The launcher accepts only explicit offline mode. Missing, malformed, or requested proxy configuration and any non-offline mode fail before a process starts; no proxy is implemented. Namespace setup/verification failures, unexpected routes/interfaces/firewall objects, missing status, startup timeout, or broker disconnect fail closed and terminate the child process group. It is not wired into `main.cjs`, does not launch Electron or a PARMAR backend, and does not prove that Chromium or its descendants stay confined. Automated tests include both mocked failure cases and live OS namespace inspection (`test/isolation-prototype.test.cjs`); the live checks run only on Linux when the required tools are available and are not a remote-traffic test.

A dedicated, unprivileged browser UID is recommended for meaningful protection against other same-UID processes. A private local socket and random capability alone do not isolate a malicious process running as the same UID: it may inspect process state, access same-UID files or sockets, or interfere with the user session. The future broker must authenticate the OS-reported peer identity and bind a short-lived capability to one launch, reject replayed sequence numbers, and accept only fixed lifecycle/status messages. It must not proxy PARMAR HTTP requests or expose approvals, execution, commands, or filesystem operations. `broker-protocol.cjs` is used by the offline probe over inherited stdin/stdout pipes and has unit coverage for strict `browser.stop` and `browser.status` messages; process creation is a fixed parent-side operation, not a broker message. It is not connected to a socket, does not authenticate kernel socket peer credentials itself, and the prototype pipe does not constitute the production cross-process IPC boundary.

#### Electron integration boundary (designed, not implemented)

Do not move `main.cjs` into the browser namespace: it owns PARMAR's trusted control window and loopback backend connection. The intended parent remains outside and spawns the exact pinned Electron executable under the reviewed namespace wrapper with a fixed argument vector and explicit browser-child role. The child role must short-circuit normal PARMAR startup, avoid the backend/control preload, create only AETHER chrome and webpage views, and use separate browser session/user-data storage. The wrapper, verifier, Electron main process, and browser descendants must all be verified outside the host network namespace; do not assume every descendant shares the wrapper's namespace inode. The live Electron 44.7.0 fixture observed the main, GPU, and Utility processes in the wrapper namespace, but Chromium sandboxed zygote and renderer processes in a second Chromium-created namespace. Production acceptance must classify the observed process types and inspect every descendant on the supported runtime; any unrecognized process or host-namespace member fails closed. The browser and every descendant must be contained in a dedicated cgroup with `cgroup.kill` and an empty-cgroup verification available to the supervisor; process-group cleanup is only a tested fallback, not proof against detached descendants. If the deployment cannot verify and enforce descendant containment, fail closed without starting Electron.

The production broker should use a private Unix-domain socket between the host parent and isolated child, separate from renderer IPC. Authenticate the accepted peer with kernel credentials (`SO_PEERCRED`), verify expected UID/PID and launch identity, and then require a short-lived capability, strict sequence numbers, bounded messages, and a fixed allowlist. Parent-to-child operations are limited to status/stop; child-to-parent messages are limited to ready/restricted/exit/error status. Navigation, webpage content, shell commands, filesystem operations, approvals, and PARMAR API forwarding are never broker operations. The child has no privileged PARMAR preload/API; webpage views continue with no preload. Keep context isolation, sandbox, Node integration disabled, web security, navigation/redirect checks, popup denial, and default-denied permissions unchanged. No Electron child mode, Unix-socket broker, cgroup supervisor, proxy, or production egress policy is implemented.

Child-process implementation is blocked pending a verified runtime/containment contract. `desktop/package.json` currently supports the development command `electron .` with `main.cjs`; the repository has no Electron packager configuration, packaged artifact, or verified packaged executable/app-path/argument behavior from which to safely define the production child's fixed launch vector. Do not infer packaged behavior from the test-only wrapper. The current Codespaces host exposes cgroup v2 but places this process in `/init`; `/sys/fs/cgroup/cgroup.kill` is root-owned and unavailable to the `codespace` user, so the required delegated cgroup kill-and-empty verification cannot be established here. Process-group signaling is not an equivalent descendant-containment guarantee. Until a supported packaged launch is validated and a reviewed supervisor with enforceable descendant ownership is available, do not add production child spawning or describe process separation as network isolation. The listener-denial requirement also remains unproven for production: the fixture's isolated Electron run is not a production child launch, and the offline Node probe is not an Electron boundary.

#### Proposed deployment contract (not implemented or packaged)

This contract targets Linux x86_64 on a native Ubuntu 24.04 desktop only. Electron 44.7.0 is pinned in `desktop/package.json` and `package-lock.json` and the development entry is `main.cjs`; there is no installed runtime-library bundle, packaging script/configuration, signed artifact, or supported deployment. The desktop code expects its HTML, CSS, renderer, preload, security, and store files beside `main.cjs` (`__dirname`); the existing store writes under Electron `app.getPath('userData')`. The app also expects a separately running loopback PARMAR backend for the control window. The browser child must not receive `PARMAR_DESKTOP_BACKEND_URL`, backend credentials, control preload assets as a usable bridge, or any PARMAR server connection.

Recommended packaging direction: adopt Electron Forge as the packaging/build orchestrator and pin its toolchain. For the first proof of concept, produce the existing PARMAR parent application plus a **separately named, unpacked child application directory** as an extra resource, for example `resources/aether-child/`. Give that directory its own `package.json` with a child-only main entry; include only the child entry, its browser chrome, browser preload, renderer, security policy, store, and required local assets. Do not implement a runtime switch in `main.cjs` that could accidentally run the PARMAR control startup in the child. Start with a directory rather than a custom-named ASAR: Electron's manual packaging documentation describes the auto-discovered resources archive as `resources/app.asar`, while an explicit directory argument is the simplest documented app-path shape to validate. Keep OS libraries and any native containment helper outside the app bundle where required and package them as reviewed signed resources. No packaging tool or secondary app bundle is present yet, so Forge is a recommendation, not an adopted or validated build.

Proposed launch contract once verified: the parent obtains its own Electron executable from `process.execPath` (never from renderer IPC, environment input, or user configuration) and constructs the child app path from `process.resourcesPath` plus the literal `aether-child`. It invokes the executable directly with Node `spawn(executable, [childAppPath], { shell: false, ... })`; no shell, script text, or arbitrary argument vector. Official Electron documentation describes launching a project directory with the Electron executable (`electron .`), defines `process.defaultApp` for an app path passed to the default executable, and documents `process.resourcesPath`; the local npm `cli.js` forwards its positional arguments to the downloaded Electron binary. This supports the *documented development app-path mechanism*, not the packaged-parent-to-custom-child-resource behavior. That packaged invocation remains unverified until a real installed artifact is built and launched. The parent must fail closed if the executable/resource is missing, outside the expected install resource directory, unreadable, or has an unexpected version/hash/signature. Use no optional Chromium switches for networking, sandbox, certificate, or proxy behavior. If a user-data override is required, derive it in trusted code from the platform's app-data root and the fixed child app identity, create it with owner-only permissions, and reject symlink/path escapes; never accept a path from IPC. The child should set/verify its own unique Electron `userData` path before `app.whenReady()`, and use a child-specific persistent partition. The parent user-data and browser child user-data must be distinct.

The child's environment is an allowlist for the supported desktop session, not an inherited arbitrary environment: preserve only required display/session variables (for example `DISPLAY`/`WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, `XAUTHORITY`, the desktop D-Bus address, and locale); provide a fixed safe `PATH` only if a reviewed native helper requires it. Strip `PARMAR_DESKTOP_BACKEND_URL`, proxy variables, Node preload/options variables (`NODE_OPTIONS`, `NODE_PATH`), library injection variables (`LD_PRELOAD`, unapproved `LD_LIBRARY_PATH`), debugging switches, and all application secrets. The exact display variables must be tested on X11 and Wayland before the contract is considered portable. The child resource directory is read-only; only its explicit child user-data directory and private IPC socket directory are writable. These paths and environment entries are proposed, not implemented.

Required package validation: build and install a real artifact; verify the parent app archive and child resource manifest, executable signature/hash/version, exact installed resource paths, direct no-shell `process.execPath` launch, child-only startup, local browser assets, preload separation, read-only resources, data-directory separation, and clean uninstall/upgrade behavior. Run those tests from the installed artifact (not the source checkout, `node_modules`, or a temporary fixture) and capture process command lines. Verify development startup remains `electron .` and cannot accidentally enter child mode. No packaged artifact has been built, so all packaged path, launch, signing, and upgrade behavior remains unknown.

Documentation evidence: Electron's [first-app tutorial](https://www.electronjs.org/docs/latest/tutorial/tutorial-first-app) uses the Electron executable with `.` as the app directory and says the executable loads the directory's package entry point; the [distribution guide](https://www.electronjs.org/docs/latest/tutorial/application-distribution) recommends Electron Forge and documents default `resources/app` / `resources/app.asar` layouts; the [process API](https://www.electronjs.org/docs/latest/api/process) documents `process.defaultApp` and `process.resourcesPath`. The installed Electron npm package's `cli.js` calls `spawn(electron, process.argv.slice(2), ...)`, forwarding its positional arguments to the downloaded Electron binary. These facts justify a disposable direct-app-path experiment and the unpacked child-directory POC; they do **not** prove that an installed, packaged Electron executable can override its default app with this custom child path. That remains a mandatory runtime test. Electron's [cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) and systemd [`Delegate=` resource-control documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html) are starting references, not evidence that delegation is configured on a deployment host.

#### Containment and lifecycle contract (not implemented)

Linux process groups are not an acceptable containment boundary. The practical target is a cgroup v2 subtree owned by a dedicated supervisor. Prefer a systemd-managed transient user service/scope or a reviewed native supervisor launched through a narrow fixed interface; it must create/own a dedicated cgroup, place the Electron child in it before allowing browser startup, and retain a handle/unique launch identity. A delegated cgroup subtree is an alternative only when an administrator explicitly provisions and verifies delegation to the application. Do not change system-wide permissions or request elevated capabilities as part of ordinary application startup. If the user systemd manager is unavailable, cgroup delegation is absent, the cgroup cannot be created/populated, or the supervisor cannot prove ownership, fail closed and do not start Electron. A supervisor must not fall back to `kill(-pid)` and call that successful containment.

The supervisor owns all launch stages, including wrapper/setup processes, Electron main, Chromium zygote, renderer, GPU, Utility/network service, crash handler, and future helpers. Readiness is emitted only after the namespace/network verifier passes, the child authenticates on its private IPC channel, and a live `/proc` census plus cgroup membership check classifies every observed process. Maintain continuous child-exit and cgroup/process membership monitoring. Record PID plus process start time (not PID alone), parent PID, executable, command line, cgroup, and `/proc/<pid>/ns/net`; require each process to be in the owned cgroup and a reviewed process-type namespace class. Unknown executable/type, any host-network-namespace member, or a process outside the owned cgroup means startup fails closed. Chromium may create additional non-host namespaces; do not require all descendants to share the wrapper's namespace inode.

On setup/spawn/readiness failure or timeout, close IPC, kill the owned cgroup, wait for the supervisor's kernel-visible cgroup process list to become empty, and return a failed launch. A child crash must be reported once, followed by cgroup kill/empty verification; no automatic restart outside the same verified launch path. On parent shutdown, send only the fixed stop operation, wait a bounded grace interval, then use the supervisor's cgroup-wide kill and verify empty before reporting clean shutdown. If cleanup cannot be confirmed, report a fatal cleanup failure and keep the parent in restricted state; never report successful shutdown or start a replacement. Any later restart requires a new launch identity and complete verification. IPC is a private Unix socket authenticated by OS peer credentials (Linux `SO_PEERCRED`) plus expected UID/PID/start time, a short-lived per-launch capability, strict sequence numbers, bounded messages, and fixed lifecycle/status operations only. The current `broker-protocol.cjs` may inform payload validation but its inherited pipes and caller-supplied PID/UID checks do not satisfy this contract.

Minimum containment validation host: a native Ubuntu 24.04 x86_64 desktop/VM with a unified cgroup v2 mount; a running systemd user manager for the logged-in desktop account; a **pre-provisioned and writable delegated cgroup subtree** owned by that account/supervisor; visible `cgroup.procs`, `cgroup.events`, and writable `cgroup.kill`; reliable `/proc` visibility; X11 and Wayland session testing; and user/network namespaces available for offline network tests. The supervisor must be able to create a launch sub-cgroup (write+search permission on the delegated parent), place the Electron root in it before application code can launch descendants (write permission to its `cgroup.procs`, or a systemd transient service that establishes membership before `exec`), issue cgroup-wide kill (write permission to that cgroup's `cgroup.kill`), and read `cgroup.procs` plus `cgroup.events` to independently confirm `populated 0`. Delegation must be established by systemd configuration or an administrator before the test; the application must not chmod/chown cgroupfs, move itself into an unrelated unit, or acquire `CAP_SYS_ADMIN`/`CAP_NET_ADMIN`. If any required ownership/access check fails, do not launch Electron. Do not infer cgroup permission from the fact that the hierarchy is mounted or a controller is listed.

The current host cannot validate this: `/sys/fs/cgroup` is cgroup v2, but this process is in `/init`, and `cgroup.kill` is root-owned; no writable delegated subtree or logged-in user systemd manager was established. A supported deployment must provide either a working user systemd manager with a reviewed transient-unit/delegation integration and verifiable cgroup ownership or explicit administrator-provisioned delegation. The precise systemd D-Bus API, permission model, helper packaging/signature, and upgrade/teardown lifecycle remain design decisions requiring review and testing; do not select `systemd-run` shell invocation as a substitute.

#### Offline-first network deployment policy and test matrix

`REMOTE_BROWSING_ENABLED` remains `false`. Stage one is a child process with **no external egress**: no proxy, no default route, no usable IPv4/IPv6 interface, no DNS resolver path, no UDP/QUIC path, and no direct host/loopback listener access. Application navigation hooks, Electron webRequest cancellation, and Chromium proxy settings are defense-in-depth only; OS policy must independently enforce the deny boundary. Namespace setup, policy verification, child readiness, and descendant ownership must complete before opening the child window. Any missing helper, unsupported kernel, unexpected route/interface/rule, listener success, verifier disagreement, or supervisor failure blocks child startup.

Any future constrained proxy is a separate design/review stage, not part of this contract. It requires a default-deny IPv4 **and** IPv6 boundary that permits only the fixed proxy endpoint and port; DNS, UDP, QUIC, direct TCP, alternate proxy configuration, and direct fallback remain blocked from the browser. The proxy itself needs a separately enforced egress policy and fixed protocol/port allowlist. It must resolve hostnames itself, normalize and validate every A/AAAA answer against prohibited ranges, pin the validated address for the actual connect (no second unconstrained resolution), revalidate every redirect and new connection, and reject mixed permitted/prohibited answers under a documented policy. Test rebinding between DNS answers and connection, split/mixed A/AAAA responses, TTL changes, redirects, alternate ports, IP literals, and failure of the resolver/proxy. No TLS interception or certificate exceptions. Unless the product explicitly accepts encrypted DNS/WebSocket traffic inside an approved CONNECT tunnel, keep those protocols unavailable; network policy cannot identify their inner protocol without TLS interception.

### Remote-browsing enforcement target (not implemented)

The production enforcement prototype should target **Linux x86_64 on a native, supported Ubuntu desktop**, not Codespaces or a generic container. Linux network namespaces isolate interfaces, protocol stacks, routing tables, and firewall rules; veth pairs can connect isolated namespaces. The kernel must be built with `CONFIG_NET_NS`. Namespace creation generally requires `CAP_SYS_ADMIN`, unless an allowed user-namespace path provides scoped capabilities; configuring links, routes, and nftables requires `CAP_NET_ADMIN` in the applicable user/network namespace. Creating the host-side veth/routing boundary may require capabilities in the initial host namespace, so this cannot be assumed rootless. The nftables rules and route topology must be managed by a separately reviewed, least-privilege helper—not by Electron startup. Do not grant those capabilities to Electron, the proxy, or PARMAR. The repository has an offline namespace verifier/probe but no production helper, egress firewall policy, proxy, safe teardown of provisioned network resources, or verifier for permitted outbound traffic. No privileged operation was attempted.

The browser namespace must have no usable direct IPv4/IPv6 route and must permit only TCP to the fixed proxy endpoint. This blocks direct TCP, UDP, DNS, QUIC, and direct WebSocket connections irrespective of Chromium proxy preferences. The proxy must itself have a separate restrictive egress policy; proxy configuration alone is not a boundary. DNS over HTTPS and WSS can be carried inside an allowed HTTPS CONNECT tunnel, so network filtering cannot distinguish those application protocols without TLS interception. Do not add TLS interception or certificate exceptions: either explicitly accept encrypted protocols through an allowed, IP-pinned destination or keep remote browsing disabled if policy requires blocking them. Every redirect/new connection must pass the same destination validation. Downloads stay denied until a reviewed download manager with safe target paths, overwrite handling, cancellation, and user-visible outcome is implemented. Browser permissions remain deny-by-default and require explicit, per-origin UI and persistence before any grant behavior is considered.

References: Linux [`network_namespaces(7)`](https://man7.org/linux/man-pages/man7/network_namespaces.7.html) documents network-stack/firewall isolation and veth pairs; [`user_namespaces(7)`](https://man7.org/linux/man-pages/man7/user_namespaces.7.html) documents capability scoping; the [upstream nftables manual](https://www.netfilter.org/projects/nftables/manpage.html) documents nftables rule management. Electron's [security guidance](https://www.electronjs.org/docs/latest/tutorial/security) separately warns about displaying untrusted remote content and recommends isolation, sandboxing, navigation restrictions, and IPC sender validation. These references describe platform capabilities and guidance, not proof that this application has configured or verified them.

Evidence required before the hard-coded navigation gate can be reconsidered: a reviewed helper and exact teardown plan; verifier checks of namespace membership and process descendants; inspected IPv4/IPv6 routes and nftables policy/counters; browser bypass tests (direct TCP, DNS, UDP, QUIC, proxy settings, WebSocket); controlled actual-socket tests for DNS rebinding, mixed answers, redirects, prohibited ranges and ports; zero hits at prohibited listeners; and proxy/resolver/helper/browser crash tests proving no fallback route. All tests must run in the isolated deployment against controlled test endpoints, with recorded commands, kernel-observed sockets and firewall counters. Electron desktop launch and normal permitted HTTPS navigation must also pass on the named supported Ubuntu desktop. None of these enforcement or real-navigation criteria has yet passed.

Validation boundaries: Codespaces can run Python/Node test suites, syntax checks, URL/origin policy tests, and mocked Electron lifecycle tests; its current environment cannot launch the GUI. A graphical Ubuntu desktop is required to verify Electron/Chromium startup and actual local UI behavior. An independently provisioned Linux isolation environment with authorized namespace/network-administration privileges and controlled DNS/listeners is required for egress tests. No Codespaces test or Electron proxy setting substitutes for that evidence.

Proposed boundary: place every Electron/Chromium process and descendant in a browser network namespace whose IPv4 and IPv6 output policy is default-deny and permits only TCP to one fixed proxy address and port. Block direct DNS, UDP, QUIC, loopback-to-host, LAN, bridge, link-local, metadata, multicast, and other routes. Place the proxy in a distinct namespace; allow it to resolve through an explicitly selected resolver and make outbound TCP connections only to permitted destinations/ports. It must reject CONNECT ports other than 443, normalize IPv4-mapped IPv6, reject a hostname if any DNS answer is prohibited, and pin the validated numeric address for the actual socket connection (no second lookup). Deny all loopback, private, link-local, metadata, multicast, reserved, and special-use ranges for both IP families. Explicitly block IPv6 transition/tunnel/translation routes unless separately covered by an equivalent verified policy. Do not expose the proxy's administration interface to the browser namespace. Firewall rules must remain restrictive if the proxy/helper exits; missing verifier evidence means no remote browsing. This design is a proposal, not a verified property.

Before any release gate can be opened, build isolated integration tests with controlled DNS and listeners. Required cases: (1) explicitly permitted controlled test traffic traverses the proxy and records the actual socket destination; (2) loopback, private, link-local, metadata, reserved, and prohibited CONNECT ports are rejected; (3) controlled DNS changes from an allowed test answer to a prohibited answer and the prohibited listener sees zero connections; (4) mixed public/prohibited answers reject the hostname; (5) IPv4, IPv6, and IPv4-mapped IPv6 are tested independently; (6) redirects to prohibited hosts fail; (7) killing the proxy leaves external traffic blocked; (8) resolver failure fails navigation; (9) browser direct TCP, DNS, UDP, QUIC, alternate DNS, and proxy bypass attempts fail; and (10) no prohibited listener receives a connection. Verify kernel-observed destination sockets and firewall counters, not only URL checks. A harness-local exception used to reach controlled test listeners must be documented and is not evidence that production public-address policy is safe. Repeat tests after startup, proxy crash/restart, browser crash/restart, and cleanup. No such network tests have run.

Rollback must first stop and verify all browser/proxy processes, then remove only specifically named resources created by the future AETHER helper. Never flush shared nftables tables/chains, change the host default policy, or detach a browser into the host network namespace during cleanup. A setup/teardown helper must be reviewed and tested before any privileged installation. Linux is the only proposed first target; Windows would need a separately verified Windows Filtering Platform/AppContainer boundary, and macOS a separately verified Network Extension/content-filter boundary. Neither is implemented, and this project does not claim cross-platform secure remote browsing.

Unsafe Python POST requests now validate any supplied `Origin` against `PARMAR_UI_ORIGIN` (or a non-wildcard numeric bind's derived origin) and reject non-`same-origin` supplied `Sec-Fetch-Site`. Duplicate, null, mismatched, or unconfigured browser origins are rejected. Requests without either header retain the existing non-browser contract; authenticated unsafe requests still require CSRF regardless. Configure the origin explicitly when using an ingress; arbitrary Host and forwarded headers are not used to derive trust.

## Authenticated session boundary (Phase 3 Slice 2)

The HTTP layer supports opaque, server-side sessions through a persistent SQLite repository. Session timeout settings are explicit: set both `PARMAR_SESSION_IDLE_SECONDS` and `PARMAR_SESSION_ABSOLUTE_SECONDS`; if neither is set, authenticated sessions are disabled. Production authentication is not implemented or claimed by this repository. The internal issuance helper is for trusted server-side callers only.

Session rows live by default at `~/.local/share/parmar/sessions.sqlite3`; set `PARMAR_SESSION_DB_PATH` to use another local path. When session timeouts are configured, `PARMAR_SESSION_STORE_KEY` must contain at least 32 bytes of stable, high-entropy server secret material and must be supplied through the server environment; it is not stored in the database or sent to browsers. The repository stores server-generated session/user IDs, authentication source, lifecycle timestamps/status, a SHA-256 hash of the high-entropy opaque cookie token, and a keyed integrity tag for each record; it never stores the plaintext token. SQLite uses a versioned schema, local-only access, restrictive directory/file permissions, and transactional expiry, revocation, and rotation. Corrupt, incompatible, missing-after-initialization, inaccessible, integrity-invalid, or wrong-key storage fails closed with a generic HTTP 503; it never falls back to an in-memory authenticated repository. No external services or network calls are used.

Authenticated cookies use `__Host-parmar_session; Path=/; Secure; HttpOnly; SameSite=Lax`. The `Secure` attribute is mandatory: the current `http://127.0.0.1` development server cannot use authenticated browser sessions over plain HTTP. Local-demo remains anonymous and continues to work without cookies or CSRF tokens. Authenticated POST requests require the session-bound `X-CSRF-Token`; `GET /api/session` returns a fresh CSRF value after a server restart but never the session token. Pending approvals require the exact authenticated user and session that created them.

### Local development authentication (Phase 5A)

An optional `POST /api/auth/development` bridge is available only for local development. It is disabled by default. It establishes exactly one fixed server-defined development principal and labels the browser session **Development Session — Unverified Identity**. This is explicitly **not identity verification**, does not accept a username or user ID, and must never be used as production authentication.

To enable it, explicitly set `PARMAR_ENVIRONMENT=development` and `PARMAR_DEVELOPMENT_AUTH_ENABLED=true`. The listener must bind to a numeric IPv4 loopback address (`PARMAR_UI_HOST=127.0.0.1`); enabling the bridge with a non-loopback bind, without configured persistent sessions/approvals, or without HTTPS fails closed. Configure both session timeouts plus `PARMAR_SESSION_STORE_KEY` (at least 32 bytes); configure `PARMAR_APPROVAL_STORE_KEY` or reuse that session key. Set `PARMAR_UI_TLS_CERTFILE` and `PARMAR_UI_TLS_KEYFILE` to a local TLS certificate/key and `PARMAR_UI_ORIGIN` to the exact HTTPS origin, including port (the UI port is 8080; for example `https://127.0.0.1:8080`). The certificate must be valid for that IP and trusted by the browser. Do not work around certificate errors or remove the cookie's `Secure` attribute. Keep the private key and session/approval store keys server-side only.

The browser's development-session request is an empty JSON object and is accepted only over HTTPS with the configured exact `Origin` and `Sec-Fetch-Site: same-origin`. The opaque session token is delivered only as the existing Secure, HttpOnly, SameSite cookie. The browser then obtains authoritative session state and its CSRF token from `GET /api/session`; CSRF remains in runtime memory. Logout revokes only the active server session. Chat, VOKKI, conversation ownership, persistent approval binding, CentralEnforcementGate, ActionBoundary, and response-safety checks are unchanged.

Production use requires a separately designed integration with a real trusted identity provider that establishes identity server-side before invoking the existing session issuance helper. Phase 5A does not implement OAuth/OIDC/SAML, production login, or identity verification.

## Restart-safe pending approvals (Phase 3 Slice 5)

Authenticated pending human reviews use a separate local SQLite store at `~/.local/share/parmar/approvals.sqlite3`; `PARMAR_APPROVAL_DB_PATH` overrides the path. Configure `PARMAR_APPROVAL_STORE_KEY`, or reuse the existing `PARMAR_SESSION_STORE_KEY`, with at least 32 bytes of stable, high-entropy server-side secret material. The chosen key is used only to derive a domain-separated HMAC integrity key and is never stored in the database or exposed to the browser. If approval integrity is not configured, or the store is unavailable, corrupt, incompatible, or fails its integrity checks, approval creation/inspection/continuation fails closed with a generic HTTP 503; there is no in-memory fallback.

The store persists the token hash, server-resolved user and session IDs, original request fingerprint, exact review response and summary, typed Chat context needed for an approved continuation, UTC expiration, and one-use state. The plaintext approval token is returned once to the authenticated page and is never stored. Each record is HMAC-protected; storage uses a versioned SQLite schema, mode-0700 data directory, mode-0600 database, and atomic consume/reject transitions. Pending records expire after five minutes using UTC time; restart cannot extend their lifetime. Consumed, rejected, and expired records remain terminal. Review/dashboard state is reconstructed only from integrity-checked server-stored fields; the client cannot supply replacement review data. Redemption still requires the active authenticated owner and exact session, CSRF validation, fresh enforcement and action-boundary evaluation, then the existing provider and response-safety pipeline. Logout/revocation makes the session-bound approval inaccessible. No approval is automatically granted and no provider runs before valid human approval.

Idle and absolute expiry timestamps are stored server-side and checked on every resolution; activity extends only the idle expiry and never past the absolute expiry. Logout/revocation and session rotation persist across process restarts. The browser keeps the opaque session token only in the HttpOnly cookie, not in JavaScript-accessible storage. The local development bridge is not a login or reauthentication mechanism and does not establish verified identity.

## Conversation ownership boundary (Phase 3 Slice 3)

Authenticated `/api/chat` requests use provider-neutral conversation and message repository protocols. The server generates conversation IDs and associates each record with the user resolved from the active session; a client-supplied ID is only a selector and must belong to that user. Authenticated context is loaded from the server-owned conversation, and client-supplied `recent_messages` are ignored. Authenticated chat responses include the server-owned `conversation_id`. User turns are stored as requests; assistant turns are stored only when the existing VOKKI contract confirms lifecycle `RELEASED`, provider `COMPLETED`, response-safety `PASS`, and disposition `RELEASED`.

The default conversation repository is a local SQLite file at `~/.local/share/parmar/conversations.sqlite3`; set `PARMAR_CONVERSATION_DB_PATH` to choose another local path. The database and its parent directory are created locally with restrictive file permissions. It uses only Python's standard-library SQLite support and makes no network calls. Repository operations are transactional and keep the existing repository interface. A missing, corrupt, incompatible, or inaccessible store fails closed with a generic HTTP 503; there is no in-memory fallback. Local-demo remains anonymous and does not create server-owned conversations. Its existing browser-local history behavior is unchanged; no local history import or migration is performed. Conversation ownership does not change approval binding or any PARMAR safety/enforcement authority.

## Authenticated conversation UI (Phase 3 Slice 4)

The browser checks `GET /api/session` before enabling requests. Authenticated chat sends the server-confirmed conversation ID and the in-memory CSRF value; it does not send browser `recent_messages`. `GET /api/conversations` lists meaningful, non-empty conversations for the authenticated user, and `GET /api/conversations/{conversation_id}` loads that owner's messages. Titles use the first sanitized user message, whitespace-collapsed and truncated to 56 characters; empty conversations are omitted. Authenticated history refreshes after authentication and chat activity. The active conversation ID alone may be retained in per-tab `sessionStorage` as a selector; it is accepted only if the authenticated user's server-owned list contains it, and messages are always loaded from the server. No session token, CSRF token, user identity, or chat content is stored there. Authenticated chat presentation is never saved to local-demo storage or audit history. Logout clears authenticated UI and the saved selector while leaving local-demo data intact. Session-ending notifications between tabs trigger a fresh server session check; a notification by itself never authenticates a tab.

New Chat clears the active selector and creates no server-side conversation until the user sends a message. Stale or other-owner IDs are discarded and cannot authorize reads. A valid browser cookie restores its server-side session after a page reload or process restart while the persisted session remains unexpired and storage is available. Conversations and sessions use separate local SQLite files and persist across server restarts. No local-demo history is uploaded or merged.

## Explicit memory ownership, consent, and retrieval (Phase 3 Slices 5–6)

Authenticated users can manage notes through `GET` and CSRF-protected `POST /api/memory` operations. Consent is held durably per user and defaults to false; saving, updating, and retrieval require current consent, while listing and deletion remain available after consent is revoked. Memory IDs, ownership, timestamps, and provenance are server-generated. Records and consent use a local SQLite database at `~/.local/share/parmar/memories.sqlite3` by default; set `PARMAR_MEMORY_DB_PATH` to select another local path. The database and parent directory are created with restrictive local file permissions. This storage is **not encrypted at rest**. Notes remain until explicitly deleted or cleared; the repository accepts at most 25 records per user and 400 characters per record. A missing, corrupt, incompatible, or inaccessible store fails closed; authenticated memory does not fall back to volatile storage.

The Memory page uses server-owned records and consent for authenticated sessions. Local-demo notes remain browser-local and are not imported. Clear credential-like content is deterministically rejected; this is a bounded safeguard, not complete secret detection.

For authenticated Chat and VOKKI, the server retrieves only currently consented memories owned by the session Principal, after request review and the existing enforcement and ActionBoundary checks. Matching is deterministic keyword overlap, not semantic search; it scans at most 25 records, up to 32 query terms from the first 1,000 request characters. At most 5 memories, each no longer than 400 characters and at most 1,200 total memory characters, enter `ChatContext`. Missing or revoked consent yields no memories. Memory is untrusted user-owned context, never authority: it cannot change risk classification, grant permissions or approval, bypass CentralEnforcementGate, ActionBoundary, provider authorization, research authorization, or response-safety checks. Approval records do not store memory content; approved continuations retrieve again after the approval and fresh enforcement checks, and use no memory if consent has since been revoked. Provider/model output never creates memory automatically. Anonymous/local-demo memory remains browser-local and separate; it is never imported into authenticated storage or Chat context. There is no automatic memory creation, embeddings, vector search, or external memory service.

## Phase 4 security hardening

Role-based provider adapters keep retrieved memory out of system guidance and pass it as a separate, labeled user-role context message before the current request. The generic HTTP adapter has no role hierarchy; it passes memory in a distinct `untrusted_context` field next to the structured PARMAR context. This separation is a boundary in PARMAR's request format, not a guarantee about how an arbitrary provider interprets content.

Authenticated conversation storage rejects writes beyond these fixed bounds: 50 conversations per user, 10,000 conversations repository-wide, 100 messages per conversation, 4,000 characters per message, 50,000 characters per conversation, and 50,000,000 stored message characters repository-wide. The chat route rejects oversized user input before provider invocation and checks that a user message plus a maximum-size response can fit. Repository appends are atomic and reject over-limit writes; no automatic history eviction is performed. A provider response too large for the remaining storage budget is not persisted or returned by that request.

Phone-awareness HTTP simulation is anonymous local-demo only; authenticated sessions are denied access to its process-local shared state. It uses simulated payloads and does not access real device APIs. The anonymous demo state remains shared within the process.

The Memory page distinguishes server-side storage from external disclosure: when a non-local provider is selected, it says that matched notes may be included only if that provider is authorized for the request. This is informational and does not grant provider authorization.

## Vokki assistant layer

VOKKI is PARMAR's human-facing communication layer, not a safety or approval authority, proof of execution, or a separate action executor. Backend responses expose one versioned `voki_contract` with separate `lifecycle`, `request_review`, `enforcement`, `approval`, `provider`, `response_safety`, and `response_disposition` fields, plus message, request ID, timestamp, and source. Unknown fields remain `UNKNOWN`; the legacy request-review status `SAFE` does not mean a provider response passed response-safety validation.

The request lifecycle reaches `ENFORCEMENT_ALLOWED` only when the authoritative gate grants permission. Chat then records `PROVIDER` → `RESPONSE_SAFETY` → `RELEASED` or `WITHHELD`. Only a provider output with response-safety `PASS` is released. `PASS` reports only that the configured validator's checks passed; it is not factual correctness or proof of real-world safety. `REVIEW`, `BLOCK`, `UNCERTAIN`, and `NOT_CHECKED` outputs are withheld; provider failure/no output is reported separately and is not presented as a response-safety failure. `execution_allowed` is permission only and never proof that a real-world action occurred.

Both `/api/analyze` and `/api/chat` create pending approvals through the same server-side store when an authenticated session may create one. Decisions are bound to the original server-held review and owner/session, expire, are one-use, and rerun `CentralEnforcementGate`; approval never bypasses enforcement or triggers real-world execution.

Browser waiting and speech do not alter the backend lifecycle. VOKKI speech output uses browser speech synthesis and speaks only contract-confirmed released responses. Voice input checks browser Web Speech API availability only after the user presses Talk and proceeds only when on-device recognition is explicitly supported and the selected language pack is already installed. `processLocally` is required and checked; no language packs are downloaded by PARMAR and no cloud transcription fallback is used. The browser requests microphone access only after the user presses Talk, and recognition is single-utterance, cancellable, and stopped when VOKKI is hidden or the page leaves. Raw audio is not sent to a recognition service; the resulting transcript is submitted through the existing `/api/chat` flow like typed text. This experimental browser capability is unavailable on unsupported browsers or languages. Genuine VOKKI volume control is not supported and no volume control is represented as available.
